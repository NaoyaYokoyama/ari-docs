# 0090_ドキュメントルール ドキュメントルール

設計書を **人間と AI の両方が同じように読める** 状態に保つためのルール。

## 1. 基本方針

- **書いてあることが仕様。書いていないことは未定**。推測で埋めず、「未決事項」に書く
- **1 つの事実は 1 か所にだけ書く**。他の場所からは ID で参照する
- **管理情報（要求元・優先度・状態・担当者・日程）は設計書に書かない**。書くのは `10_要件定義/0090_課題一覧.md` だけとする
- **実装が正になるものは設計書に写さない**（例: `CREATE TABLE` 文はマイグレーションが正）。設計書には実装から読み取れない「意味・理由・制約」を書く
- 実装を変えたら、同じ作業の中で設計書も更新する

## 2. フォルダ構成

| フォルダ | 内容 | 状態 |
|---|---|---|
| `00_概要/` | システム概要・用語集・本ルール | 整備対象 |
| `10_要件定義/` | 要件一覧、機能要件、非機能要件、課題一覧（管理情報） | 整備対象 |
| `20_設計/00_画面設計/` | 画面 | 整備対象 |
| `20_設計/10_API設計/` | API | 整備対象 |
| `20_設計/20_DB設計/` | テーブル・ビュー | 整備対象 |
| `20_設計/30_バッチ設計/` | バッチ | 整備対象 |
| `20_設計/40_帳票設計/` 〜 `50_外部IF設計/` | 帳票・外部IF | 該当なし（一覧とテンプレートのみ） |
| `30_単体テスト/` | 単体テスト仕様（機能要件ごと） | 整備対象 |
| `40_結合テスト/` | 結合テスト仕様（機能をまたぐ一連の操作） | 整備対象 |
| `50_運用/` | 起動・停止、ビルド、設定、DB、バッチ、トラブル対応の手順 | 整備対象 |
| `80_ツール/` | 開発環境の構築（`00_linux/`・`10_windows/`）、開発支援ツール | 整備対象 |
| `90_アーカイブ/` | 廃止した文書の置き場 | 整備対象 |

各フォルダには次の 2 種類の固定ファイルを置く。

| ファイル | 役割 |
|---|---|
| `0000_〇〇一覧.md` | そのフォルダの文書の一覧（ID・名称・状態・概要） |
| `9900_〇〇テンプレート.md` | 新しい文書を作るときにコピーする雛形 |

## 3. 番号の付け方（区分コード）

ファイル名と ID の番号は **4 桁** とし、**先頭 2 桁を区分、次の 2 桁を区分内の連番** にする。区分ごとにファイルが並ぶので、同じ機能の文書を探しやすい。

| 区分 | 内容 | 主な文書 |
|---|---|---|
| `00` | 共通（全体・複数機能にまたがるもの） | 共通操作、共通レイアウト、マイグレーション履歴 |
| `01` | 利用者 | 利用者の識別、ユーザー |
| `02` | ホーム | 検索 |
| `03` | フォルダ（ノード） | ノード、ノード同期 |
| `04` | Note | Note |
| `05` | Wiki | Wiki |
| `06` | お気に入り | お気に入り |
| `07` | 設定 | ユーザー設定 |
| `08` | Markdown ビューア | Markdown ビューア |
| `09` | 管理 | バックアップ |

- 新しい機能を追加するときは、この表に区分を追加してから採番する
- 区分内の連番は `01` から振る。固定ファイルは区分 `00` で、`0000`・`0010`・`0020` … と 10 刻みにする（例: `0000_システム概要`、`0010_用語集`、`0090_ドキュメントルール`）
- 一覧は `0000`、テンプレートは `9900` とする

## 4. ファイル名

- 先頭に番号か ID を付ける（CLI で補完しやすくするため）
- 個別の文書は `<ID>_<名称>.md` とする（例: `FN0501_Wiki.md`、`API0505_Wiki更新.md`）
- **front matter の `id` は必ずファイル名と一致させる**
  - 個別の文書: ファイル名の最初の `_` より前（`FN0501_Wiki.md` → `FN0501`）
  - 固定ファイル（ルール・一覧・テンプレート）: 拡張子を除いたファイル名（`9900_APIテンプレート.md` → `9900_APIテンプレート`）

## 5. ID

形式の `0000` のうち、先頭 2 桁が区分（3 章）、後ろ 2 桁が区分内の連番。

| 種類 | 形式 | 例 |
|---|---|---|
| 要求 | `RQ0000` | `RQ0501`（Wiki の要求） |
| 機能要件 | `FN0000` | `FN0501`（Wiki） |
| 業務ルール | `<機能ID>-BR00` | `FN0501-BR02`（機能ごとに連番） |
| 画面 | `SCR0000` | `SCR0501`（Wiki 画面） |
| API | `API0000` | `API0505`（Wiki 更新） |
| テーブル | `TBL0000` | `TBL0501`（wiki テーブル） |
| バッチ | `BAT0000` | `BAT0301`（ノード同期） |
| メッセージ | `MSG0000` | `MSG0501`（Wiki 作成成功） |
| 単体テスト | `UT-<対象ID>` | `UT-FN0501` |
| 結合テスト | `IT0000` | `IT0401`（Note の一連の操作） |
| 運用手順 | `OP0000` | `OP0001`（起動・停止） |
| ツール | `TL0000` | `TL0001`（開発環境構築） |

- 一度使った ID は再利用しない。廃止した文書は `status: 廃止` にして `90_アーカイブ/` へ移す
- 文中で他の文書を指すときは ID で書く（例: 「`FN0501-BR02` を満たすこと」）

## 6. ファイル先頭の定型情報（front matter）

すべての文書の先頭に YAML 形式で書く。AI や整合チェックはここを機械的に読む。

```yaml
---
id: FN0501            # 必須。ファイル名と一致させる（4 章）
title: Wiki          # 必須。名称
type: 機能要件        # 必須。概要 / 要件 / 機能要件 / 画面 / API / テーブル / バッチ / 単体テスト / 結合テスト / 運用 / ツール / ルール / 一覧 / テンプレート / 管理
status: 確定          # 必須。下表のいずれか
related: [SCR0501, API0505, TBL0501]  # 関連する文書の ID（無ければ []）
updated: 2026-10-11  # 必須。最終更新日（YYYY-MM-DD）
---
```

| status | 意味 | 実装してよいか |
|---|---|---|
| 草案 | 書きかけ・検討中 | ✕ |
| レビュー中 | 内容は揃っており確認待ち | ✕ |
| 確定 | 合意済み | ○ |
| 廃止 | 使わなくなった | ✕ |

## 7. 書き方

- 見出し 1（`#`）は `<ID> <名称>` とする
- **1 文に 1 つの事実**を書く。条件が複数あるときは箇条書きか表にする
- 「など」「適宜」「必要に応じて」「基本的に」のような曖昧な言葉を使わない。対象をすべて書くか、未決事項にする
- 権限は「誰が・何を・できる／できない」を表で書く
- 理由が自明でない決定には理由を書く（後から AI や他の人が判断を覆さないため）
- 該当しない項目は削除せず `-`（なし）と書く。空欄は「未記入」とみなす
- テンプレート内の `<!-- -->` は記入ガイド。記入が終わったら消してよい
- 日付は `YYYY-MM-DD`、日時は `YYYY-MM-DD HH:MM` で書く
- **図は mermaid で書く**（Markdown の ```` ```mermaid ```` ブロック）。draw.io などの別ファイルは使わない。差分が git で見え、AI も読み書きできるため
- 画面のレイアウトは ```` ```text ```` ブロックの簡易図で書く

## 8. 決定事項と未決事項

- 仕様を決めたら、その文書の「決定事項」に **日付・内容・理由** を追記する
- 決まっていないことは「未決事項」に書く。AI は未決事項に該当する実装をする前に、必ず人に確認する
- 未決事項が決まったら、決定事項へ移して本文にも反映する
